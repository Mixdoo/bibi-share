# 单 Agent、SubAgent 与智能体团队：工作原理与实操

之前我们已经了解过 DeepSeek Harness 中工具插件和技能插件的工作原理。这次把它作为一个熟悉的任务，学习三种 Agent 工作模式：一个 Agent 怎样独立完成任务，父 Agent 怎样委派子任务，以及多个 Agent 怎样组成团队协作。

实践中，三种模式都会收到同一个需求：

> 请分析这个项目中工具插件和技能插件的工作原理，解释它们如何被加载，以及 Agent 如何使用它们，并用源码支持你的结论。

分析从这个问题出发。相关代码在哪、有哪些模块、模块怎样连接，都由 Agent 自己探索。我们关注的是探索过程中的任务拆分、上下文传递、工具使用、沟通和结果整合。

## 一、先理解一个 Agent 怎样工作

### 1. 从一次回答到持续执行

用户提出源码分析需求后，Agent 最初并不知道答案。它需要先了解项目，再寻找相关入口、读取实现、追踪调用关系。有时第一次搜索的信息不足，它就根据已有线索继续搜索；有时读到的代码修正了之前的判断，它就调整后续分析。

Agent 循环负责推进这个过程：把任务、已有上下文和可用工具提供给模型，执行模型发出的工具调用，把工具结果加入会话，再继续下一步。模型决定下一步要做什么，运行时负责实际执行工具并保存结果。

![单 Agent 的循环与会话历史](https://generated-media-morris2.oss-cn-hangzhou.aliyuncs.com/shared-images/2026/10/02/9839e5cfaa204362b946dc27b1bcdaac.png)

这个过程可以拆成五步：

1. **接收任务。** 用户的问题进入当前会话。
2. **决定下一步。** 根据当前已有信息，选择继续查找、读取、验证，或回答用户。
3. **执行工具。** 搜索、文件读取等工具实际执行操作，返回结果。
4. **更新上下文。** 工具调用与结果进入会话历史，成为下一步判断的依据。
5. **继续或结束。** 若还需要信息，就继续调用工具；能给出回答时，结束这一轮工作。执行也可能因错误或取消而结束，因此“停止运行”本身不代表任务已经完成。

在 DSH 中，一次模型请求及其工具调用构成一个步骤（step）；一次用户任务的处理可以包含多个步骤，组成一个轮次（turn）。工具结果会促使循环继续，让模型有机会使用刚获得的信息。Agent 也可以直接回答，并非每一步都必须调用工具。

### 2. Session 保存什么

Session 是会话记录。用户输入、模型输出、工具调用和结果等事实通过会话日志保存，后续请求的历史从日志中派生。Agent 因此能够利用前面读过的内容继续工作。

这并不表示项目所有文件自动进入上下文。Agent 要通过工具获得具体内容，或者接收其他输入；一次读取也可能只返回文件的一部分。它当前能据以判断的信息，取决于已经提供给这次请求的上下文。

对源码分析来说，这一点直接影响结果：文件存在于工作区，并不等于 Agent 已经读过；回答里提到一个函数，也需要用实际读取结果支持。

### 3. 多次工具调用为什么仍是单 Agent

一个 Agent 可以连续调用工具，也可以在运行时允许的范围内并行调用适合并行执行的工具。例如同时读取两个互不依赖的文件，仍然由同一个 Agent 接收结果并决定下一步。

区分 Agent 数量，要看是否创建了新的执行主体及其会话。工具调用数、模型请求次数、回答段落数，都不能直接当成 Agent 数量。

### 4. 单 Agent 模式的特点

在单 Agent 模式下，任务的理解、资料收集、判断与汇总都由同一个 Agent 完成。它可以先分析工具插件再分析技能插件，也可以先通读项目结构后交叉追踪，具体阅读顺序由它决定。

这种方式协调过程简单，已有发现能够直接用于后续分析。任务扩大后，同一个 Agent 也需要管理更多信息：哪些结论已证实、哪些入口还没看、哪些判断需要修正，都集中在同一条会话中。是否适合继续使用单 Agent，要看任务复杂度和实际结果，不能只按文件数量判断。

## 二、SubAgent：把一部分工作委派出去



### 1. 子 Agent 自己也有执行循环

当任务可以拆分时，父 Agent 可以把其中一部分交给子 Agent。子 Agent 接收任务后，有自己的会话与执行过程，能够搜索、读文件、继续判断，最后返回结果。

![SubAgent 的委派、独立执行与返回](https://generated-media-morris2.oss-cn-hangzhou.aliyuncs.com/shared-images/2026/10/02/775deb810a5d44dab7d37cc277b55a3d.png)

父 Agent 的职责也随之变化。它既要完成自己的工作，还要说明子任务、接收子级报告、检查遗漏和矛盾，并形成最终回答。子 Agent 返回一段文本之后，父级仍需判断这段结果是否足以支持整项任务。

以本次源码分析为例，父级可以先了解项目，再判断哪些分析能够独立开展。它可能按工具与技能拆分，也可能将入口定位或某项结论复核交出去。这些是可能的任务划分，具体方案应由初步探索决定。

### 2. 一次委派需要传递哪些信息

委派通常需要明确三件事：子级要解决的问题、已经知道的必要背景、需要返回的结果。对于源码分析，“找到相关实现并说明依据”通常比“帮我看看”更容易得到可用报告。

子级拥有独立上下文，不会自动持续同步父级新发现的一切。DSH 支持新建子级以及继承已有历史的 fork 等方式；初始带入多少历史取决于创建方式。即使开始时继承了历史，之后各自的新发现仍需要通过报告或消息传递。

独立 Session 也不意味着独立工作目录或独立操作系统进程。本教程使用 DSH 的进程内委派能力，父子可以访问同一个项目。分开的是会话执行与上下文，具体文件是否隔离取决于运行配置。

### 3. 父子如何配合完成任务

典型过程是：父级理解总体问题，建立明确的子任务；子级自行查找与分析；父级继续处理其余工作；子级返回结论和依据；父级再核对与整合。

并行并非每次都能发生。如果父级下一步必须依赖子级结果，它就需要等待。如果还有独立工作，它可以先做。SubAgent 提供委派能力，是否能缩短耗时还取决于任务拆分、依赖和执行资源。

报告也是信息交接的一部分。子级查阅的大量材料经过总结后传回父级，能够减少父级直接处理的内容，但总结也可能遗漏细节。因此，涉及最终结论的关键源码位置应随报告一起返回，供父级复查。

### 4. 一次性子级与可继续子级

一次性子级运行后交回一个结果；可继续子级保留可续接的会话身份，父级可以给同一个子级发后续问题。

在当前 DSH 基础组合中，普通 `subagent` 工具配置为可继续模式，`subagent_fork` 默认是一次性模式。这是组合配置的选择，不能把“新建”与“可继续”、“fork”与“一次性”当成天然等同的概念。

本次实践使用可继续子级。第一轮分析完成后，我们还会请父级联系同一个子级核对其结论。目标身份保持不变，才能体现继续已有工作；另外创建一个子级属于新的委派。

## 三、智能体团队：让成员围绕共同任务协作



### 1. 每个成员仍然独立执行

智能体团队由 Lead 和具名成员组成。Lead 负责组织工作、创建成员、协调与汇总；成员各有自己的 Agent 循环和 Session，完成分配到的任务。

![智能体团队的任务板和成员消息](https://generated-media-morris2.oss-cn-hangzhou.aliyuncs.com/shared-images/2026/10/02/2de79aa24f814906815d24c78113ede7.png)

团队在这些 Agent 之间提供成员身份、共享任务板和消息能力。在 DSH 中，Team 构建于可继续子级能力之上，是显式启用的实验性功能。

### 2. 共享任务板解决什么问题

多个成员工作时，需要知道哪些事情已经有人在做、谁负责、进展怎样、哪些任务还在等待前置结果。任务板让这些信息有一个共同可读写的位置。

一个任务可以记录目标、负责人、状态和依赖。例如两项独立分析完成后，汇总任务才具备开始条件。依赖声明能够阻止尚未就绪的任务被认领，但任务就绪不会自动让负责人开始运行；推进工作仍需要 Agent 的执行与协调。

成员状态与任务状态也要区分。一个成员当前处于 `inactive`，只表示此刻没有执行轮次，不能据此认定它的任务成功或失败。判断任务是否完成，要看任务状态、实际交付和相关结果。

### 3. 成员间消息解决什么问题

普通父子委派主要沿父子关系传递信息。在 DSH Team 中，成员可以直接给其他成员或 Lead 发消息，交流发现、请求澄清、核对关联结论。

在源码分析中，一名成员可能发现自己研究的机制使用了另一名成员正在研究的能力。它可以把实际位置和疑问发过去，由对方核对后回答。这一轮交流应建立在实际发现上；它不需要事先知道模块叫什么，也不需要用户提前给出调用关系。

消息到达仍有执行过程：正在工作的成员在后续步骤接收消息；非活动成员可因消息启动或恢复。返回 `queued` 表示消息已保存、等待投递，不表示对方已经处理。成功排队后不应仅因为暂时没有回复就重发同一条消息。

### 4. 共享工作并不自动合并所有上下文

团队成员在当前 DSH Team 实现中共享工作目录，各自维护会话上下文。A 读过一个文件，B 不会因此自动知道文件内容。A 需要通过消息给出相关发现，B 也可以自己读取对应源码。

任务板共享的是任务信息；它不是把所有人的完整对话合成一份上下文。有效协作依赖明确的任务、足够具体的消息，以及对关键结论的复查。

团队增加了并行探索和直接协调的机会，同时也增加了创建成员、分配任务、交换信息和汇总的开销。它适合确实有分工与沟通需求的任务；成员越多，并不自然意味着结果越好。

## 四、把三种工作模式放在一起看


| 比较项     | 单 Agent        | SubAgent        | 智能体团队              |
| ------- | -------------- | --------------- | ------------------ |
| 谁推进任务   | 一个 Agent       | 父 Agent 与被委派的子级 | Lead 与具名成员         |
| 上下文如何组织 | 当前 Agent 的会话历史 | 父子各自维护上下文       | 各成员维护上下文           |
| 工作怎样拆分  | 自己安排内部步骤       | 父级给出子任务         | Lead 协调，任务板记录分工与依赖 |
| 信息如何交流  | 工具结果回到当前 Agent | 子级报告及父子后续消息     | 成员间直接消息与共享任务状态     |
| 最终如何整合  | 当前 Agent 自己完成  | 父级核对并汇总         | 本实践由 Lead 核对并汇总    |
| 主要成本    | 一条会话承担全部探索与核对  | 委派说明、结果交接与父级验收  | 分工、状态维护、消息与集成      |


DSH 插件页的三个入口对应不同层次：Agent 循环驱动每个 Agent 运行；子智能体提供委派与子级管理；智能体团队增加成员间协作。打开相关设置本身不会替你完成任务拆分，仍需要 Agent 在实际任务中调用对应能力。

“并行工具调用数”控制一个 Agent 步骤内的工具并行；“最大递归深度”控制子级还能向下委派几层；子级容量和团队成员上限则控制相应 Agent 数量。它们影响不同资源，不能相互替代。

## 六、实践一：单 Agent 独立完成



### 第一步：新建会话并发送任务

选中 DSH 项目工作区，发送以下完整提示词：

```text
请分析这个项目中工具插件和技能插件的工作原理，解释它们如何被加载，以及 Agent 如何使用它们，并用源码支持你的结论。

请由你一个 Agent 独立完成，不启动子智能体或团队成员。自行探索项目，定位相关实现，逐步核对关键调用关系。

最终请给出清楚的原理说明、一张关系图，以及支持关键结论的源码文件和行号；尚未确认的地方请说明。只读分析，不修改项目文件。
```

提示词只规定任务、工作方式和交付要求。Agent 需要自己决定先看什么、如何定位入口、什么时候继续追踪，以及何时已有足够依据回答。

### 第二步：理解执行过程

展开当前会话的工具调用，可以看到搜索或读取返回了什么信息，以及 Agent 后续沿哪些线索继续工作。具体顺序由本次运行决定，无需要求它固定先查某个目录。

这里的关键关系是“刚得到的信息如何帮助下一步”。如果搜索结果出现新的实现入口，Agent 继续读取它，就是工具结果参与后续判断；如果第一次线索不足，它更换检索方式，就是同一循环在继续推进。

有多个读取调用同时进行，也仍可能是单 Agent。只要没有创建独立子级或团队成员，任务的探索与整合就仍由当前 Agent 完成。

### 第三步：在同一会话继续核对

收到报告后，发送：

```text
请从刚才的报告中选出一条关键结论，重新沿实际源码核对它。说明哪些代码直接支持这条结论，是否存在需要修正或补充的地方，并更新相应说明。
```

这次输入继续使用当前会话。Agent 可以依据已有发现继续查证，无需从用户那里重新获取完整背景。核对后可能确认原结论，也可能修正它；两种结果都能够体现会话内持续工作的方式。

### 第四步：检查任务是否完成

确认报告确实解释了问题、引用了实际源码，并且图与文字一致。再结合执行记录确认全部工作由当前 Agent 完成。最终答案里写“独立分析”本身，不足以说明执行时没有委派。

## 七、实践二：父 Agent 委派 SubAgent



### 第一步：新建会话并指定委派方式

保持 Team 关闭，选中同一工作区，在新会话发送：

```text
请分析这个项目中工具插件和技能插件的工作原理，解释它们如何被加载，以及 Agent 如何使用它们，并用源码支持你的结论。

这次请使用父 Agent + 一个可继续 SubAgent 的方式完成。你先初步了解项目，再自主选择一项边界清楚、适合独立分析的子任务，通过 subagent 工具委派出去。给子级说明任务目标、必要背景和需要返回的结论及源码依据。

子级工作期间，你继续处理其余可以独立推进的内容。收到子级结果后，由你核对关键依据，处理遗漏或分歧，再汇总回答。

最终请给出清楚的原理说明、一张关系图，以及支持关键结论的源码文件和行号；尚未确认的地方请说明。你和子级都只读分析，不修改项目文件。
```

这里把拆分工作交给父级。它需要先知道项目大致情况，再决定哪一部分适合委派。子任务可以有不同划分，不能用“是否恰好按照某两个模块分工”判断委派是否成立。

### 第二步：查看实际委派内容

展开 `subagent` 调用，查看父级实际给子级的问题和要求。一次有效委派应让子级知道要研究什么、需要返回什么，而不是让它猜测父级意图。

调用创建子级后，会有可继续子级的身份信息。子级在自己的会话里读取与分析；父级可以继续做独立工作，也可能因依赖结果而等待。具体是并行还是等待，应根据实际轨迹理解。

收到子级报告后，查看父级是否把它与自己的发现关联起来。父级应对最终解释负责，尤其需要核对报告中影响整体结论的依据。

### 第三步：继续同一个子级

初次报告完成后，在父会话发送：

```text
请继续联系刚才那个子智能体，让它从自己负责的分析中选一条关键结论，重新沿源码复核，并返回依据及需要修正的地方。

使用后续消息继续同一个子级，不要新建。收到它的回复后，你核对并更新最终报告。
```

这里由父级通过后续消息把任务交给原子级。核对消息目标与之前的子级身份是否一致，才能确认它续接了既有会话。

子级能够继续使用自己此前积累的背景，但父级新增的发现仍需要明确告诉它。若希望子级检查父级的新结论，父级应随消息提供该结论和相关依据。

### 第四步：处理未按预期委派的情况

如果 Agent 直接自己完成、没有调用 `subagent`，可以补充：

```text
请实际调用 subagent 完成一次委派。由你选择一项适合独立核对的问题，交给子级，收到结果后再由你整合。请使用当前环境可用的真实委派能力。
```

若返回工具不可用，应先检查当前组合与设置；提示词无法凭空提供未挂载的能力。若无法继续原子级，也应根据工具错误排查当前子级形态与状态，不能将新建子级当作续接成功。

## 八、实践三：智能体团队协作完成



### 第一步：启用团队并新建会话

在插件页启用“智能体团队”，确认配置生效后新建会话，选择同一项目工作区。发送：

```text
请分析这个项目中工具插件和技能插件的工作原理，解释它们如何被加载，以及 Agent 如何使用它们，并用源码支持你的结论。

这次请使用智能体团队。你担任 Lead，初步了解项目后，自主拆分分析任务，创建两名具名 teammate，并通过共享任务板明确目标、负责人和必要的依赖关系。

每名成员自行定位与研究负责的内容，向团队提供结论和源码依据。成员发现彼此分析有关联或存在疑问时，请直接通过团队消息交流并核对；完成初步分析后，再让两名成员相互检查对方的一条关键结论，并更新任务状态。

你负责协调尚未解决的问题，等待所需成员完成工作，核对关键依据，最后汇总为清楚的原理说明、一张关系图，以及支持关键结论的源码文件和行号；尚未确认的地方请说明。

所有成员都只读分析，不修改项目文件。
```

成员名字、职责和任务划分由 Lead 根据初步探索决定。这里要求两名 teammate，是为了让直接沟通与任务协作清楚可见；并未替它们指定待发现的模块或正确答案。

### 第二步：理解成员与任务的对应关系

在执行记录中查看 `spawn_teammate`，了解创建了哪些成员、各自接到什么任务；再通过团队面板或任务工具结果查看任务板。

成员列表回答“有哪些 Agent、当前是否在运行”，任务板回答“有哪些工作、谁负责、当前进行到哪里”。两者并不相同：一个成员可以先后处理多个任务，一个任务也可能因前置依赖而暂时无法认领。

Lead 可能先建任务，也可能先创建成员后分配。只要成员收到明确工作、任务状态得到维护，调用顺序可以随实际探索变化。

### 第三步：理解成员间的核对

查看成员间的 `send_message`，重点读消息传递了哪些新信息：某项发现、对应源码、尚未解决的问题，或者对另一成员结论的修正。

原提示词已经要求成员互查一条关键结论。这使协作有具体目的：各自分析完成后，需要把足够的依据交给对方，让对方能够独立判断。互查可能确认结论，也可能暴露遗漏，无需预设一定出现分歧。

如果本次执行没有完成互查，在同一会话补充：

```text
请让两名 teammate 直接交换各自的一条关键结论及源码依据，并分别核对对方的结论。把核对结果通过团队消息发给对方和你，更新相应任务状态，再由你修订最终说明。
```

Lead 转述成员发现能够传递信息，但如果要使用 Team 的直接成员沟通能力，应能找到成员之间的真实消息。两段以不同名字署名的回答并不代表两个成员真的协作过。

### 第四步：让 Lead 完成整合

成员完成任务后，Lead 应检查不同报告能否形成连贯解释，处理重复、遗漏和不一致，并对关键引用进行核对。最终关系图应由实际发现形成，不能把几张彼此矛盾的局部图直接拼在一起。

若 Lead 过早结束，而必要成员仍未完成，可继续要求：

```text
请检查成员与任务的当前状态，确认哪些工作还没有完成。让需要继续工作的成员完成并返回结果，处理未解决的问题后，再给出汇总回答。
```

等待工具只负责等待变化。若需要工作的成员处于非活动状态，应通过适当消息让它继续；反复等待本身不会完成任务。任务板显示完成后，还需要看实际交付是否满足原问题。

## 九、从这次实践中理解三种模式

三次分析可能得到相近的架构结论，因为它们研究的是同一份源码。最终答案相近并不会抹去执行方式的差异。

单 Agent 的信息收集和整合集中在一个会话中。SubAgent 把一部分探索放到独立子会话，通过委派与回报衔接。团队进一步让成员共享任务状态，直接交换发现，并围绕共同结果协调工作。

选择方式时，可以先看任务需要什么：能在一条会话中连贯推进，单 Agent 通常更直接；有清晰独立子任务，可以委派 SubAgent；多项工作需要持续交换信息并管理依赖，可以使用团队。是否更快、更省资源或更准确，需要根据实际执行比较，不能由 Agent 数量推导。
